## Phase 0 diagnostics

Wi-Fi event callback now records STA disconnect reason code, last event code and AP transition counts with constant-time writes. The regular loop emits a transition record and a 30-second summary with firmware ID, uptime, STA state/RSSI, reconnect count, free/min heap, maximum service-loop gap, HTTP error/timeout counts. These counters are also in `/data`. Reset reason/brownout indication and the other service counters already existed in telemetry. Event codes and reset reasons are diagnostic evidence, not a root-cause conclusion. No battery voltage is inferred.

Reproducible supervised comparison: capture serial and `/data` for five minutes idle, five minutes held/manual movement, hazard activation/clearance, standalone SoftAP, and STA with each tested router; repeat near low battery while an external meter records supply voltage under load. Record timestamps, firmware, router/channel, distance, reset reason, disconnect reason, heap, RSSI, loop gap, HTTP counts and observed motor state. Keep wheels clear and physical STOP/power cutoff accessible. Compare counts and event ordering; do not convert qualitative responsiveness into latency measurements. The current code does not measure motor STOP latency.

## Phase 1A software gate

- Volatile per-robot Manual flame/gas permission is enabled only by a confirmed action during a live 2,500 ms browser control session while gas/flame is active. The existing ~450 ms telemetry poll carries the session token as a link heartbeat, independently of held movement commands; an explicit heartbeat endpoint is also available. A direction release uses `RELEASE`: it stops PWM immediately but does not revoke permission. The 750 ms movement dead-man also stops motion without revocation. Session timeout, mode change, explicit STOP, critical temperature/sensor fault and 2,000 ms stable hazard clearance revoke permission and invalidate the old token so delayed directions cannot restart motion. The next direction requires a new browser session and a new press. Temperature remains non-exempt. AUTO still uses the original hazard hold, continuous-clear wait and scan path.
- The existing Wi-Fi/HTTP transport does not authenticate a human identity or encrypt the bearer session token. The token identifies a current browser control session on the trusted local network; it is not a claim of secure remote authorization. A separate authenticated transport requires an approved architecture change. Hardware testing is pending.
- The current sensor layout cannot establish the complete swept body envelope of any held Manual pivot or spin. The new Manual motion gate therefore returns `PIVOT_CLEARANCE_UNKNOWN` for Left/Right until a validated clearance mechanism is supplied. This intentionally disables Manual turning, including outside hazard override; do not present it as a working turn feature. Forward now blocks on either confirmed low front IR zone and ultrasonic caution/fault. Explicit held Manual Reverse remains available under the 750 ms dead-man; rear clearance is not sensor-verified.
- The original short AUTO reverse remains unchanged and is still a separate unverified-rear-coverage limitation. No new automatic reverse was added.
- The dashboard displays the override warning continuously while permission is active, retains independent flame/gas alarm telemetry, offers an explicit confirmation/ACK/failure action, and displays the rear-coverage warning. `/data` reports permission, inhibit reason and session liveness.
- `pio run -e esp32-s3-n16r8`: PASS; 53,692/327,680 RAM (16.4%), 1,020,477/6,553,600 flash (15.6%). No compiler warning in the final output. Native MinGW C++ policy and motion-gate tests: PASS/PASS, built with `-std=c++11 -Wall -Wextra -Werror` and run locally. An initial compile failed on a const mismatch and was fixed before this pass.

## Phase 1B software gate

- Pre-change source-based simulation of equal 30/30 cm side choices in the normal algorithm: LEFT -> RIGHT -> LEFT -> RIGHT; the existing 1,200 ms blocked retry reset both obstacle and old stuck attempt counters. This simulation is not a robot motion observation.
- `ENABLE_STUCK_RECOVERY_V2` is OFF by default. The normal 35-degree turn target, existing AUTO hazard recovery and legacy short AUTO reverse were left in place. With the flag ON, the old forward/IMU STILL/static-sonar stuck maneuver is disabled so it cannot launch its blind reverse as a competing recovery manager.
- V2 counts completed valid L/F/R avoidance scans over a 15-second window, left/right reversals, short failed forward command periods, and repeated no-safe-side scans. Equal distances alone do not trigger it. A five-second sustained clear forward command period clears the suspicion history; it is not measured translational progress. Invalid readings break valid-cycle evidence; three consecutive invalid scans within the window require assistance.
- After suspicion, V2 stops, discards the normal avoidance maneuver and takes a new non-blocking L/F/R scan without a new reverse. The fitted three rays, forward IR zones and no rear sensor cannot certify the complete body width and pivot sweep. Even if the provisional 50 cm front value is met, V2 therefore enters persistent `TRAPPED_HOLD` with motors OFF, an assistance-required event and telemetry. It requires an operator mode rearm. A provisional 25-degree target is recorded as a future calibration candidate; **no V2 turn or forward escape is enabled on Rev A**. `ESCAPE_TURN` and `ESCAPE_VERIFY` are state-policy placeholders with native tests, not operational motion claims.
- V2 attempt counts survive ordinary 1,200 ms blocked backoff. Safety and operator STOP interrupt scanning. A hazard during the scan returns to the existing AUTO hazard-clear/rescan path; an already latched trapped hold still requires operator intervention. The normal feature-OFF motor path retains its existing behavior.
- Native MinGW simulated trace test: PASS for isolated obstacle, symmetric readings without cycle evidence, oscillating turn choices, sustained clear forward command time, repeated blocked scans, invalid sensor readings, bounded scan timeout, persistent hold, manual/STOP/hazard abort in the policy, and attempt budget across aborted windows. Neither firmware variant was flashed or physically tested.
- Suggested supervised layout: wheels elevated first for STOP, mode, sonar fault and IMU outage; then a wide open floor for ordinary obstacle regression; a wide straight corridor for no false trap; equal-distance side panels and a U-shaped enclosure for repeated oscillation/blocked scans. Record scans, state transitions, motor state, alarm and actual external measurements. Expect normal navigation with OFF. ## Focused correction pass (later than Phase 1C)

The Phase 1A and 1B sections above record what those individual commits implemented and tested. The focused correction commit restores held operator-supervised Manual Left/Right. A matching front IR zone, a fresh near-front ultrasonic reading (<=7 cm), or an available fresh side-inspection obstruction vetoes the affected turn; the service loop also stops an active turn on matching IR/near-front evidence. The 750 ms movement dead-man, explicit STOP, temperature and session gates remain. Rear and complete pivot-sweep clearance are not sensor verified.

V2 remains OFF by default. When enabled, repeated valid avoidance history triggers a motor-off fresh L/F/R scan. Finite side readings above the provisional 30 cm threshold, direction-specific IR, and fresh healthy IMU allow a committed side. The manager uses the existing gyro-Z turn integration with the V2-only 25-degree target, stops after each increment, and rescans. Three stable finite front samples (spread <=5 cm) with median >=50 cm and finite usable sides permit a fresh-front-checked 250 ms forward trial; a full fresh scan after the trial must still meet the provisional gate to return to NORMAL. The first side has at most 3 turns; the opposite side is considered only after a fresh scan, with at most 6 total turns and 30 seconds. Invalid required sensing, STOP, hazards, mode takeover, turn timeout, lost previously present Wi-Fi transport, or exhausted limits stop the attempt. The trapped hold remains latched until deliberate mode rearm. No new V2 reverse was added.

These values are provisional research criteria, not proof of a passable robot-width corridor, measured translation, or actual 25-degree motion. The AUTO browser control session is Manual-only; V2 monitors loss of a Wi-Fi interface or dashboard telemetry poll that was present when escape began, while fully standalone AUTO can run without a browser connection. The AUTO poll is an unauthenticated link signal. A supervised bench test must establish collision clearance, turn calibration, link behavior and useful progress before enabling V2 by default. See [FOCUSED_CORRECTION_PASS.md](FOCUSED_CORRECTION_PASS.md) for source and test evidence.

## Recovery and communication stability correction (later physical-test build)

The user reported a physical boxed-in case (L/F/R roughly 14/9/11 cm) in which V2 scanned without turning, and STA dashboard Live/Stale/Offline oscillation while Manual remained responsive. These are reported pre-change observations. No post-change hardware result is claimed. Earlier sections describe their own commits and software gates.

The source cause of the boxed-in hold was the V2 decision requiring each candidate side to exceed 30 cm. The V2-only decision now requires valid finite L/F/R and a healthy IMU, compares available left/right space, and chooses the greater side. Equal sides use recorded failed-turn history and remain committed within a bounded sequence. A candidate is vetoed only by its directional IR zone or a side distance <=7 cm, reusing the existing near-contact threshold. Both vetoed sides stop into the 2,500 ms cooldown, then get a fresh scan and automatic retry. Normal AUTO 35-degree obstacle turns are unchanged. Recovery still uses gyro-integrated 25-degree increments, motor-off fresh L/F/R scans after each, at most 3 increments per side and 6 per round, and a stable valid front >=50 cm followed by a fresh-front-checked 250 ms forward trial and post-trial full rescan. The forward trial no longer requires both sides above 30 cm; existing front and IR guards remain. No new reverse was added.

The already present small /ping endpoint now drives browser connection liveness and renews an existing Manual session token when supplied. The browser polls ping every 650 ms after each response, polls full /data every 850 ms after each response, and labels Live for a recent ping with current telemetry, Stale for a recent ping with telemetry older than 3,000 ms, and Offline only when ping has not succeeded for more than 3,000 ms. These are scheduled intervals and software rules, not measured network latency. STOP aborts pending ping and telemetry fetches. The synchronous server bounds /data socket writing to 125 ms and an idle incomplete request to 250 ms; a stalled telemetry client is closed so the loop can accept urgent control. STA enables Arduino automatic reconnect and loop-driven nonblocking retries starting at 1,500 ms with bounded 3,000/6,000/8,000 ms backoff, resetting after connection. AP+STA and dynamic-IP origin handling remain. This does not prove a worst-case physical STOP latency.

Software gate: native C++ policy/integration/origin/trace tests and Python capture-schema test passed; embedded dashboard JavaScript syntax and Live/Stale/Offline transitions passed in local headless Edge. PlatformIO esp32-s3-n16r8 build passed with V2 ON; RAM 58,724/327,680 bytes (17.9%), flash 1,037,013/6,553,600 bytes (15.8%). These values are build reports, not physical measurements. Supervised tests still need to establish actual pivot clearance, turn angle, recovery progress, STOP response, STA roaming/reconnection, and SoftAP behavior. No firmware was flashed.
